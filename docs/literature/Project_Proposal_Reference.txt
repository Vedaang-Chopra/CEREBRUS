Adaptive Looped VLM — Research Vision & Implementation Blueprint
Nov 22, 2026 · @Vedaang Chopra
TL;DR
Build Version B first: an existing text-guided visual-token selector, plus a lightweight controller that picks the visual budget k and the loop count R per input, on TML-d24-varloop-research. Defer the learned, text-conditioned vision encoder (Version C) until Version B shows a real gain.
Central question: can extra recurrent passes compensate for fewer visual tokens, and can a learned policy allocate both resources better than any fixed setting at matched FLOPs?
Primary backbone: thinkingmachines/TML-d24-varloop-research (26.4B MoE, 3.4B active, middle 12 layers looped 1–5 times, trained across that range). Fallback: a small, cheap model for every method test before it touches the 26B model (Section 3).
What is already taken: text-guided token pruning (SparseVLM, CRISP, AdaptInfer), joint token + layer-skip adaptation (SmartVL, AdaVSkip), and retrofitting a VLM into a looped model (RR-VLM). We do not claim any of these.
What we can defend (subject to the checks in Section 9): (1) the first controlled measurement of the trade between visual tokens and loop passes on one set of looped weights; (2) a test of whether loops can substitute for tokens on reasoning-limited items but not perception-limited ones; (3) a reward-trained (k, R) controller compared against heuristic and supervised allocation; (4) whether attack success changes with k and R, measured conditional on capability.
Safety is a measured axis and a possible constraint, not the headline. Safety-aware training is added only if Phase 6 measurements justify it.
Dec 3 (course): environment, the (k × R) evaluation grid, oracle-headroom analysis, a controller trained on the grid's full reward table (cost-sensitive learning, not RL), and the safety grid. January (paper): on-policy GRPO with LoRA, an encoder-side variant if justified, safety-constrained training, a second backbone, and full baselines.
First gate (end of Nov 24): varloop loads on A40s, runs at R = 1–5 with outputs that change with R, and gives ScreenSpot grounding well above zero. If any of these fails, switch to the fallback plan in Section 3.
1. Research vision
We post-train an existing looped VLM so it decides, per input, how much it looks (visual token budget k) and how long it thinks (loop passes R), and we measure what that does to accuracy, cost, latency and safety. No pretraining-scale compute is used.
1.1 Problem
A VLM spends the same compute on every input: the same number of visual tokens, and in a looped model the same number of passes. Prefill cost in a looped decoder is roughly the product of the two axes:
C_{\text{prefill}}(k, R) \approx 2\,\bigl(P_{\text{pre}} + P_{\text{coda}} + R\,P_{\text{core}}\bigr)\,\bigl(k\,N_v + N_t\bigr) \; + \; C_{\text{ViT}}(N_{\text{patch}}) \; + \; C_{\text{attn}}
Here P are active parameters per token, N_v the full visual token count, k ∈ (0, 1] the kept fraction, N_t the text tokens. For varloop, P_pre + P_coda ≈ 2.4B and P_core ≈ 1.0B per pass (derived from the model card's 3.4B / 5.4B / 7.4B at 1 / 3 / 5 passes). Because the axes multiply, a joint choice can save more than either alone. Pruning tokens before the decoder also makes every pass cheaper.

1.3 Safety as a measured axis
Safety is measured along both axes, not pursued as a separate project. Two published results make it non-trivial in opposite directions. Fewer loops removes refusal in text-only looped models faster than it removes task ability (Running Fewer Loops Removes Refusal). Query-based token compression can improve VLM safety while most other pruning degrades it (Token-Pruning-Induced Vulnerabilities, ICML 2026). Which effect dominates in a looped VLM under GUI prompt injection is unmeasured.

2.3 Verified gaps vs speculative claims
Verified gap: no paper found that varies visual budget and weight-shared loop depth jointly on one checkpoint. SmartVL and AdaVSkip vary non-recurrent layer compute.
Verified gap: no paper found that measures prompt-injection or jailbreak success across loop depth in a VLM.
Speculative until checked: that substitution (H2) is a new finding. SmartVL already reports dataset-dependent allocation (POPE prefers tokens, TextVQA prefers compute). Our claim must be item-level, causal (controlled grid), and specific to recurrence, or it collapses into theirs.
Speculative until checked: that reward-trained allocation beats supervised allocation. AdaVSkip already adds a GRPO stage on top of supervised routing. Our training-method novelty is weak; treat it as engineering, not a headline.
Weekly check owed: arXiv for "varloop", "TML-d24", "looped VLM". The model is two days old; depth sweeps by others are likely within weeks.

3.2 Why varloop, beyond recency
It removes a whole phase. Elastic-depth healing was our riskiest step; Thinking Machines already trained 1–5 passes into the weights.
Clean causal comparisons. One set of weights at five depths means depth effects are not confounded with different checkpoints, which is the stated purpose of the release.
The headroom is visible already. The card shows MMMU Pro rising 63.6 → 72.1 from 1 to 4 passes while PerceptionBench peaks at 3 (53.9) and drops at 5 (52.7). Different tasks want different depths.
Variable-resolution vision tower lets us implement the token budget inside the encoder path (resolution) as well as after it (pruning), which is the distinction the vision asks for.
Scientific cost to state up front: 3 passes dominated varloop's later training, so other depths may under-perform what depth-specific training would give. Report this as a confound, and treat per-depth numbers as "this checkpoint", not "looped models in general".
3.3 Engineering budget on 8× A40 (48 GB)
Inference: 4 BF16 replicas × 2 GPUs (tensor- or pipeline-split via device_map="auto"). If NVFP4 runs on Ampere through any kernel path, 8 single-GPU replicas.
Controller training: trivial. It trains on cached features (Section 5), one GPU, minutes.
LoRA on the backbone (paper stage): frozen BF16 base ~53 GB sharded across 8 GPUs with FSDP; LoRA rank 16 on q/k/v/o of layers 6–17 only. Feasible but slow; budget days, not hours.
On-policy GRPO (paper stage): generation is the bottleneck. Use short-answer tasks only, G = 4–8 rollouts per prompt, and a reward that needs no judge.
3.4 Go / no-go for the backbone (end of Nov 24)
☐ Loads in BF16 across 2 A40s; a 20-item smoke test gives sane answers at R = 3.
☐ Outputs and accuracy change monotonically-ish with R on a 100-item GQA slice (R = 1 visibly worse).
☐ Throughput ≥ 1 item/s per replica on short-answer VQA, so the Phase 1–2 grid fits in under ~24 GPU-hours.
☐ ScreenSpot-v2 grounding at R = 3 well above zero (target ≥ 30% point-in-box; set the exact bar before running).
Any box fails → diagnose for at most one day, then switch: token-axis study on Inkling-2-Mini (R fixed) and the loop axis on Ouro + a small vision projector, reported as two separate studies.

5. Proposed architecture
Version B is the plan: a frozen varloop backbone, a parameter-free text-guided token selector, and a ~1.5M-parameter controller that picks one of 15 actions (k, R) per input before the decoder runs. Version C (a trained, question-conditioned vision encoder) is gated on B's results.

proposed architecture · varloop backbone, Version B; shapes from config.json
The controller decides first; k then shrinks the visual sequence either by resolution (inside the encoder path) or by pruning (after the projector), and R sets how many times layers 6–17 run.

5.2 How each decision is made
Text conditions vision in two places: the controller sees the question when choosing k, and the selector scores tokens by question relevance. Neither changes the ViT's internal computation in Version B.
Visual budget k ∈ {25, 50, 100}%: chosen by the controller; applied by resolution (saves ViT + decoder compute, loses fine detail everywhere) or pruning (saves decoder compute only, keeps the most relevant detail). Phase 2 picks the mechanism by measurement.
Loop count R ∈ {1..5}: chosen by the controller, once per item, before prefill; the same R is used for every generated token in Dec. Per-token depth (MoR-style) is a January option.
Interaction: the controller picks the pair jointly from one softmax, so it can learn "look less, think more". With pruning, the decoder sees k·N_v tokens on every pass, so prefill cost scales with k·R (Section 1.1).
5.3 Recurrent KV cache
Status: unverified until step 0.5. The likely layout is one KV cache per layer application, i.e. 12 + 12R caches of [k·N_v + T, 8 heads, 128] for K and V. In BF16 that is 4 KB per token per layer application, so R = 5 with 1,000 tokens is about 72 × 4 KB × 1,000 ≈ 0.3 GB, small on a 48 GB GPU. Pruning shrinks every cache by the same factor k. Sliding-window layers (window 1024) cap the cache for 20 of the 24 layers. If the code shares KV across passes instead, record it: that changes both memory numbers and what an extra pass can attend to.

Phase 1: loop-depth baseline (Nov 24–26)
Objective: accuracy, latency, FLOPs at R = 1..5, k = 100%, on the fixed evaluation set (Section 7).
Procedure: greedy decoding, max 32 new tokens for VQA, 64 for grounding; system prompt and answer-extraction templates frozen before the run; 1 seed (greedy is deterministic up to kernel nondeterminism; record it).
Output: results/grid.parquet with one row per (item, k, R): prediction, correct, prompt tokens, visual tokens, analytic FLOPs, TTFT, decode time, peak memory.
Verification: R = 3 accuracy within a few points of public numbers where comparable; re-run 50 items to measure nondeterminism.
Go/no-go: oracle-R accuracy minus best fixed-R accuracy ≥ Y points, or ≥ Z% fewer mean FLOPs at equal accuracy. Set Y, Z before running (suggestion: Y = 3, Z = 20).
Phase 2: visual token budgeting (Nov 25–28)
Objective: full grid k ∈ {25, 50, 100}% × R ∈ {1..5} = 15 cells.
Two budget mechanisms, compared at matched visual-token counts: (a) post-projector top-k pruning with a text-guided score; (b) input-resolution scaling so the ViT emits ≈k·N_v tokens. Mechanism (b) also saves ViT compute; (a) keeps fine detail where it matters. This is the inside-vs-after-encoder comparison.
Selectors for (a): random (control), uniform-pool (text-agnostic), text-sim (pre-decoder cosine), prelude-attn (attention from last text token at prelude layer L_p, FastV/SparseVLM-style). Pick one primary selector on a 200-item dev split; freeze it.
Verification: k = 100% reproduces Phase 1 exactly; random at k = 25% is worse than the primary selector.
Artifacts: iso-FLOP plot, exchange-rate map (accuracy surface over k, R), oracle labels per item, H2 analysis (Section 7.4).
Go/no-go: H1 margin met on the grid; at least one benchmark shows a non-additive k×R interaction (Section 7.4). If neither, write up the measurement as the contribution and stop method work.
Phase 3: adaptive controller (Nov 28–Dec 1)
Objective: a small policy π(a | x) over the 15 actions a = (k, R).
Features (cheap, computed before the decision): mean-pooled text embeddings from the LM embedding table, pooled ViT features of a 224 px thumbnail (so the decision comes before the full-resolution encode), image size, question length. Optionally the prelude hidden state on text only. All cached once per item.
Model: 2-layer MLP, 512 hidden, 15-way softmax. ~1.5M parameters.
Reward: r(x, a) = 1[correct(x, a)] − λ · FLOPs(x, a) / FLOPs(x, a_max). Sweep λ ∈ {0.05, 0.1, 0.2, 0.4}.
Three training regimes, in order of appropriateness for Dec 3:
Supervised imitation: label = cheapest correct action (ties to fewest FLOPs; unsolvable items → a_max or a_min, ablate). Cross-entropy. Baseline only.
Full-information cost-sensitive learning: the grid gives r(x, a) for all 15 actions, so maximise E_{a∼π}[r(x, a)] directly with exact gradients. This is the right method for Dec 3. Do not call it GRPO or a bandit: nothing is sampled and nothing is unobserved.
Offline contextual bandit: hide all but one logged action per item (from a uniform logging policy), train with inverse-propensity or doubly robust estimates. Run only as a check that the method works when the full table is not available (it won't be for long generations).
On-policy GRPO (January): needed once decoding is stochastic, outputs are long, or the backbone is trained jointly (LoRA), so rewards for unchosen actions are unknown. G = 4–8 sampled actions per prompt, group-normalised advantages.
Verification: policy on the test split traces a Pareto curve as λ varies; at λ → 0 it recovers best-accuracy action; at large λ it collapses to a_min.
Go/no-go: closes ≥ X% of the oracle gap at matched mean FLOPs, beating every heuristic (Section 7.2). Fail → report negative result with the oracle analysis.
Phase 4: adaptive vision encoder (January)
What is feasible with pretrained weights: (i) resolution as an action, already in Phase 2 (no training); (ii) text-conditioned early dropping: fuse a pooled question embedding into ViT layer ℓ (QA-ViT-style FiLM or cross-attention adapter), score tokens there, drop the bottom (1−k) for layers ℓ+1..23. Train only the adapter + scorer + LoRA on ViT layers ≥ ℓ with distillation to the full model's decoder logits on ~100–300k VQA samples.
What is not feasible: retraining the ViT, or a new tokeniser.
Go/no-go: encoder-side dropping must beat post-projector pruning at equal tokens by a pre-set margin and show measured ViT latency savings. Else drop Phase 4.
Phase 5: joint optimisation (January)
LoRA (r = 16) on attention of layers 6–17 + controller, trained with on-policy GRPO on short-answer data; KL to the base policy. Optional: per-segment depth during decoding.
Go/no-go: joint training beats the frozen-backbone controller from Phase 3 at matched FLOPs on held-out benchmarks.
Phase 6: safety evaluation and alignment (measurement Dec; training Jan)
Measurement on the 15-cell grid as in Section 8. Training (depth-randomised safety SFT/DPO, or a safety term in the controller reward) only if capability-conditioned attack success varies with k or R by more than the pre-set margin.
Phase 7: final evaluation and paper (January)
Baselines and ablations from Section 7, two controller seeds, three evaluation seeds where sampling is used, paired bootstrap CIs, a single command reproducing the headline table.

7.4 Testing the substitution hypothesis (H2) without circularity
The trap: labelling an item "reasoning-limited" because extra loops helped it, then "finding" that loops help reasoning-limited items. Labels must come from probes independent of the varloop grid.
Text-sufficiency probe (perception vs reasoning): a separate model gets a dense, high-resolution description of the image (OCR + caption from a different VLM, e.g. a Qwen3-VL model at full resolution) plus the question, with no image. If a strong text-only LLM answers correctly from that description, the information needed is extractable, so failure is a reasoning-or-integration failure → reasoning-limited. If it fails while a full-resolution VLM succeeds, the bottleneck is visual detail → perception-limited.
Resolution-sensitivity probe: on a different VLM, compare accuracy at full vs quarter resolution. Large drop → perception-sensitive.
Pre-registration: probe thresholds fixed on the dev split before the test grid is examined. Items the two probes disagree on are reported separately.
Model (logistic, item random effect):
\Pr(\text{correct}_{i,k,R}) = \sigma\big(\beta_0 + \beta_k \log k + \beta_R R + \beta_{kR} (\log k \cdot R) + \beta_{kRT} (\log k \cdot R \cdot T_i) + \ldots + u_i\big)
T_i = 1 for reasoning-limited items. Substitution predicts β_kR < 0 (more loops soften the penalty of fewer tokens) mostly through β_kRT, i.e. only for reasoning-limited items. Fit with statsmodels mixed GLM or, simpler, a cluster bootstrap over items for the iso-FLOPs comparison: at equal FLOPs, does (low k, high R) beat (high k, low R) on reasoning-limited items and lose on perception-limited items?

8.2 Metrics that cannot mistake incapability for safety
For each GUI item, three outcomes: correct target, decoy (attack success), neither (failure).
\text{ASR}_{\text{cond}}(k, R) = \Pr\bigl(\text{decoy} \mid \text{clean version correct at the same } (k, R)\bigr)
Report raw ASR, conditional ASR, and clean accuracy side by side in every table. A cell with low raw ASR and low clean accuracy is incapable, not robust.
For harmful-request sets: compliance rate on harmful prompts and refusal rate on matched benign prompts; a model that refuses everything scores 100% "safe" and 100% over-refusal.
Worst case over reachable actions: max over (k, R) the policy can choose, not only the average.
8.3 Questions, each answerable from the grid
Does conditional ASR rise as R falls (prediction from text looped LMs)?
Does it fall as k falls with a text-guided selector (prediction from the query-based compression result), and rise with a text-agnostic selector?
Does the efficiency-trained controller route attacked inputs to cheaper actions than their clean twins? Compare action distributions for paired items.
Is there a cell that is both cheaper and safer than the default (k = 100%, R = 3)? If so, that is a positive safety result for adaptive compute.
8.4 When to train for safety (Phase 6, January)
Trigger: conditional ASR at some reachable action exceeds the default's by ≥ the pre-set margin (suggest 10 points, CI excluding zero), or the controller shifts attacked inputs toward vulnerable actions. Then, in order of cost:
Reward shaping (cheapest): add −μ · 1[attack succeeds] to the controller reward on a training split of injected items; the controller learns to spend compute where it buys robustness. Report over-suspicion on benign on-screen instructions.
Action constraint: a minimum R or k when an injection detector (prelude probe) fires.
Depth-randomised safety LoRA: SFT or DPO on refusal and injection-ignoring targets with R sampled per step, following the random-depth result. Baseline against SafeBridge-style depth-aware DPO.

9.4 Results that weaken or kill the hypothesis
Oracle headroom < Y points: per-input allocation is not worth it on this checkpoint.
Accuracy surface is additive in log k and R (no interaction): loops and tokens are independent, so H2 fails; the paper becomes a measurement note.
Varloop at R ≠ 3 is uniformly poor (training-distribution artefact): depth findings are about this checkpoint's training mix, not looping.
Controller gains vanish under measured latency (MoE routing overhead, batch effects).

11.2 Inference pipeline (pseudocode)
def run_item(item, k, R, model_R, selector, mechanism):
    img, q = item.image, item.question
    if mechanism == "resolution":                     # inside-encoder budget
        img = resize_to_token_budget(img, k)           # ViT emits ~k*N_v tokens
    inputs = processor(images=img, text=prompt(q))
    vis = model_R.encode_images(inputs)               # TODO: hook name from model_notes.md
    if mechanism == "prune" and k < 1.0:               # post-encoder budget
        scores = selector.score(vis, text_embeds(inputs))
        vis = keep_topk(vis, scores, k, keep_order=True)  # keep spatial order
    t0 = cuda_event()
    out = model_R.generate(inputs_with(vis), max_new_tokens=32, do_sample=False)
    return Row(pred=decode(out), flops=flops(k, R, n_vis=vis.shape[1]), ttft=..., ...)
11.3 Controller training (pseudocode, full-information objective)
# R_table[i, a] = correct_i(a) - lam * flops_i(a) / flops_i(a_max)   from grid.parquet
for x, r in loader(features, R_table):                 # x: [B, F], r: [B, 15]
    logits = policy(x)                                 # [B, 15]
    p = logits.softmax(-1)
    loss = -(p * r).sum(-1).mean() - beta * entropy(p)  # exact expected reward
    loss.backward(); opt.step()
# eval: a* = argmax policy(x); report acc, mean FLOPs, gap closed vs oracle

13.2 Self-review: contradictions found and resolved
Learning track vs deadline. Two full days of exercises before Phase 0 would push Gate 0 to Nov 25. Resolved: exercises run in the download and evaluation gaps (Section 12).
"GRPO" for the Dec controller. With greedy decoding and a full reward table, nothing is sampled, so calling it GRPO or a bandit would be wrong. Resolved: the Dec method is full-information cost-sensitive learning; GRPO is reserved for January (Phase 3 text).
Version C was asked as the goal. It is the most expensive and least likely to yield a clean result before Dec 3. Resolved: C is gated on B's results (Section 5).
Encoder-side vs post-encoder budget. Resolution scaling is an encoder-side budget that needs no training. Resolved: it is compared against pruning in Phase 2, before any encoder training.
Novelty of RL allocation. AdaVSkip, VisionThink and AdaptVision already use RL for compute allocation. Resolved: the training method is not claimed as a contribution.
Compute claims. All GPU-hour figures are estimates until step 0.8; the plan says where they get replaced.
